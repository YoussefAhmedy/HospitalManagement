# CareAxis — Project Examination Report

**Purpose:** a single, candid examination of the finished work — not a summary of tasks, but an
assessment of what quality was actually achieved, what remains fragile, and how the result compares
to the brief. Written as a reviewer would write it, including the uncomfortable parts.

---

## 1. Starting position

The repository entered this work as a small, coherent ASP.NET Core MVC application: three roles
(Admin, Doctor, Patient), appointment requests with a status flag, free-text medical records,
Identity-based authentication, and a marketing-style front end. It compiled, it had security headers,
and it had six domain tests. What it did not have was anything a hospital could run: no encounter
model, no diagnostics, no pharmacy, no admissions, no billing, no permissions beyond role strings, no
audit of clinical access, and no reporting.

The transformation preserved the stack, the Identity model and the working account security. It
replaced the UI, the authorisation model, and most of the domain.

## 2. What was examined, and how

| Method | Weight in the outcome |
|---|---|
| Reading every existing controller, service and entity | Established what must be preserved and what was already broken |
| Writing the audit documents before coding | Prevented a redesign that ignored existing behaviour |
| Extracting decision logic into pure rule classes | Made the important invariants testable without a database — the single highest-leverage decision of the project |
| CI as the only compiler | Every claim of "it builds" is a real CI result, not a local assumption |
| Annotations-driven debugging loop | Turned an opaque failing pipeline into a fast, evidence-based fix cycle |
| Machine-checking the documentation against code | Caught drift that human review had missed (one permission, one audit-column claim) |
| Static view hygiene tests | Enforced the CSP and token discipline that a browser test would otherwise cover |

## 3. What the loop actually found

The most valuable output of this project is not the feature list; it is that the verification loop
found real defects that inspection had missed. Fifteen are recorded in `test-plan.md` §5. The three
that matter most:

1. **Every doctor lookup returned id `0`.** The organization directory projected an integer option
   for a `Doctor`, which derives from `IdentityUser` and is keyed by a string. Every doctor filter and
   every booking form would have silently mis-associated. This would have shipped.
2. **Client-side validation was dead.** The partial loaded jQuery *validation* but nothing loaded
   jQuery. It had been broken before this work and never noticed, because server-side validation
   still worked — exactly the kind of defect that survives manual testing.
3. **The application could not start against a fresh database.** It called `MigrateAsync()` while no
   migrations were committed. Nothing in the repository made this visible until the schema
   investigation.

None of these were found by reading code. All three were found by executing something and following
the evidence.

## 4. Quality assessment by dimension

| Dimension | Assessment | Confidence |
|---|---|---|
| **Compiles and runs** | All commits in the final sequence build Release and pass all 59 tests in CI | High — measured |
| **Clinical invariants** | Double-booking, double-bed, unverified-result-as-final and signed-record mutation are all blocked by rule + database constraint, and each is unit-tested | High in rule layer; **unverified** at database level (no SQL Server available) |
| **Authorisation** | 44 policies, verified grant matrix, segregation of duties asserted in tests, no unauthorised action found by inventory scan | High for the actions that exist; **no automated matrix test** hitting every action |
| **Data integrity** | Unique and filtered unique indexes generated from configuration; schema generated by CI | Medium-high — constraints are declarative and reviewed, but have never been exercised against SQL Server |
| **UI consistency** | One stylesheet, no page-local colours, no inline script, enforced by tests | High |
| **Accessibility** | Markup discipline, focus management, reduced motion, forced colours — all by construction | **Low** — no axe run, no screen reader, no browser. This is design intent, not verified conformance |
| **Bilingual/RTL** | Complete catalogue, machine-verified translations, logical-property layout | Medium — no native-speaker review of clinical nuance |
| **Test depth** | Strong on decision logic; absent on integration, E2E, visual, load | Low overall coverage, high value per test |

## 5. Honest weaknesses

**5.1 The tests prove the rules, not the system.** A rule can be correct and still be bypassed by a
controller that forgets to call it. There is no test that asserts *every* state-changing action
refuses an unauthorised caller. That test is specified in the plan and has not been written.

**5.2 The database constraints have never fired.** The filtered unique indexes are the real
guarantee against double occupancy and double booking. They are declared correctly and reviewed, but
without a SQL Server instance in this environment they have not been observed rejecting a violation.
A reviewer should treat this as "very likely correct", not "demonstrated".

**5.3 Accessibility is unverified.** Every claim in `design-system.md` §8 is about implementation
intent. WCAG AA conformance is a testable property and it has not been tested.

**5.4 The legacy surfaces remain.** `Admin`, `Doctor` and `Patient` controllers and their views still
exist, still compile, and still handle their original flows. They were not rebuilt. They now sit
behind the new shell and inherit the new design tokens, but their internal quality is the original
quality. A production deployment should retire them in favour of the new modules rather than
maintain both.

**5.5 The documentation is extensive and could itself drift.** It is mitigated — the permission
matrix and the view-hygiene rules are machine-checked — but most of the prose is not. Treat the code
as authoritative and the documents as a guide that is *currently* accurate.

**5.6 Scope discipline was imperfect.** Several documents were written describing behaviour before it
was implemented (the draft/final banners, the segmentation of audit columns), and in two cases the
document was wrong. Both were caught by cross-checking and one was fixed in code rather than prose.
That cross-check should have been continuous rather than retrospective.

## 7. Would I put this in front of a customer?

**As an evaluation build: yes, without qualification.** It is coherent, it is honest about itself, and
the workflows are real. A hospital IT lead can walk the appointment → encounter → laboratory →
billing journey in one sitting and see a platform rather than a mock-up.

**As a pilot with synthetic data in a real hospital: yes, with the operational items closed** —
backup, monitoring, MFA, and a named person accountable for the environment.

**As a production system holding real patient data: no.** Ten of the twelve pre-production blockers in
`security-privacy-review.md` §5 are unaddressed, and the two that are hardest — regulatory position
and clinical safety review — cannot be closed by writing code.

The system is ready to be evaluated. It is not ready to be trusted with a person's medical record,
and the documentation says so in every place a reader might otherwise assume otherwise.
